# SAMS — Student Leave Management & Approval Workflow Enhancement

## 1. Objective

พัฒนาระบบยื่นใบลานักศึกษาใน SAMS (Student Attendance Management System) ให้เชื่อมโยงกับ Approval Workflow, รายวิชาที่นักศึกษาได้รับผลกระทบจากช่วงเวลาการลา และระบบเช็คชื่อเข้าเรียน (Attendance)

ให้อ้างอิงข้อมูลและแนวทางจากแบบฟอร์มใบลาของวิทยาลัยการสาธารณสุขสิรินธร จังหวัดตรัง

ระบบต้องรองรับการเลือกหลายรายวิชาแบบ Dynamic โดยไม่จำกัดจำนวนไว้ที่ 4 วิชาตามแบบฟอร์มกระดาษ

## 2. Student Leave Submission

นักศึกษาสามารถดำเนินการดังนี้

- กรอกข้อมูลใบลาป่วยหรือใบลากิจส่วนตัว
- ระบุวันที่เริ่มลาและวันที่สิ้นสุดการลา
- ระบุเหตุผลและข้อมูลประกอบตามแบบฟอร์ม
- เลือกรายวิชาที่ได้รับผลกระทบจากช่วงเวลาการลา
- เลือกได้หลายรายวิชา โดยไม่มีการกำหนดจำนวนสูงสุดแบบตายตัว
- ตรวจสอบข้อมูลก่อนส่งคำร้อง
- ติดตามสถานะคำร้องและความคิดเห็นของผู้พิจารณาแต่ละขั้นตอน

นักศึกษาสามารถจัดการเอกสารดังนี้

- แสดงใบลาในรูปแบบเอกสารที่ใกล้เคียงแบบฟอร์มต้นฉบับ
- พิมพ์ใบลาได้
- Export เป็น PDF
- แสดงข้อมูลนักศึกษา รายละเอียดการลา ประวัติการลา ความเห็นผู้พิจารณา และความเห็นอาจารย์ผู้สอน
- จัดรูปแบบสำหรับพิมพ์ A4
- ใช้ภาษาไทยและฟอนต์ที่เหมาะสม
- ไม่แสดงช่องว่างหรือข้อมูลที่ไม่เกี่ยวข้องกับใบลานั้น

ตาราง "ประวัติการลา" (คอลัมน์ **ลามาแล้ว** / **ลาครั้งนี้**) แสดงเป็น **จำนวนวัน** แยกตามลาป่วยและลากิจ:
"ลามาแล้ว" นับเฉพาะคำร้องที่อนุมัติแล้วของปีการศึกษาของวันที่อ้างอิง (รวมวันที่อยู่นอกช่วงภาคการศึกษาที่บันทึกไว้ เช่น หลังจบภาคการศึกษาสุดท้าย)
และ "ลาครั้งนี้" คำนวณแบบ live ขณะกรอกฟอร์ม ไม่นับคำร้องที่กำลังแก้ไขซ้ำใน "ลามาแล้ว"

ระบบควรแสดงรายวิชาที่เกี่ยวข้องโดยพิจารณาจากตารางเรียนของนักศึกษาในช่วงเวลาที่ลา แต่ต้องให้นักศึกษาสามารถเลือกหรือยกเลิกรายวิชาได้ตามความเหมาะสม

ต้องอ้างอิง Course Offering / Section / Class Schedule / Academic Term ที่มีอยู่ในระบบ ไม่ใช้ชื่อวิชาเป็นตัวเชื่อมหลัก

## 3. Course-specific Leave Review

คำร้องลา 1 รายการสามารถเชื่อมโยงกับหลายรายวิชาได้

สำหรับแต่ละรายวิชาที่นักศึกษาเลือก ให้สร้างข้อมูลการส่งคำร้องไปยังรายวิชานั้น โดยมีรายละเอียดอย่างน้อยดังนี้

- คำร้องลาอ้างอิง
- รายวิชา / Section / ภาคเรียน
- ช่วงวันที่และเวลาที่ได้รับผลกระทบ
- อาจารย์ผู้สอนที่รับผิดชอบ
- สถานะการพิจารณารายวิชา
- ความคิดเห็นของอาจารย์ผู้สอน
- วันเวลาที่พิจารณา
- ผู้พิจารณา

อาจารย์ผู้สอนมีสิทธิ์พิจารณาเฉพาะรายวิชาที่ตนเองรับผิดชอบ หรือได้รับมอบหมายอย่างถูกต้องเท่านั้น

อาจารย์ผู้สอนสามารถ

- ดูข้อมูลคำร้องและช่วงเวลาการลา
- ดูข้อมูลนักศึกษาที่จำเป็นต่อการพิจารณา
- ให้ความคิดเห็นประกอบการลา
- บันทึกสถานะการพิจารณารายวิชา เช่น Pending, Reviewed, Acknowledged หรือ Rejected ตามนโยบายที่กำหนด
- ดูประวัติการพิจารณาของรายวิชาที่รับผิดชอบ

การพิจารณาของอาจารย์รายวิชาต้องแยกจากการอนุมัติคำร้องหลัก หากนโยบายวิทยาลัยไม่ได้กำหนดให้อาจารย์รายวิชาเป็นผู้อนุมัติคำร้องหลัก

ห้ามถือว่าการที่อาจารย์รายวิชารับทราบหรือให้ความคิดเห็น เท่ากับการอนุมัติใบลาโดยอัตโนมัติ

## 4. Student Leave Approval Workflow

ออกแบบระบบการพิจารณาคำร้องลาให้สอดคล้องกับแบบฟอร์มใบลาของวิทยาลัย โดยมีผู้พิจารณา 3 ขั้นตอนตามลำดับดังนี้

### 4.1 อาจารย์ที่ปรึกษา — บันทึกความเห็น

- ตรวจสอบรายละเอียดคำร้องลาและข้อมูลประกอบ
- บันทึกความเห็นของอาจารย์ที่ปรึกษา
- สามารถระบุข้อเสนอแนะเพิ่มเติมได้
- ส่งต่อคำร้องไปยังหัวหน้าหน่วยหลักสูตรตามลำดับ Workflow
- ไม่มีสิทธิ์อนุมัติหรือไม่อนุมัติคำร้องหลัก เว้นแต่ได้รับมอบหมายตามสิทธิ์ที่กำหนด

### 4.2 หัวหน้าหน่วยหลักสูตร — บันทึกความเห็น

- ตรวจสอบรายละเอียดคำร้องลาและความเห็นจากอาจารย์ที่ปรึกษา
- บันทึกความเห็นของหัวหน้าหน่วยหลักสูตร
- สามารถระบุข้อเสนอแนะเพิ่มเติมได้
- ส่งต่อคำร้องไปยังผู้มีอำนาจอนุมัติตามลำดับ Workflow
- ไม่มีสิทธิ์อนุมัติหรือไม่อนุมัติคำร้องหลัก เว้นแต่ได้รับมอบหมายตามสิทธิ์ที่กำหนด

### 4.3 ผู้มีอำนาจอนุมัติ — บันทึกผลการพิจารณา

ผู้มีอำนาจอนุมัติเป็นผู้พิจารณาผลสุดท้ายของคำร้องลา โดยต้องดำเนินการดังนี้

- ตรวจสอบรายละเอียดคำร้องลา
- ตรวจสอบความเห็นจากอาจารย์ที่ปรึกษา
- ตรวจสอบความเห็นจากหัวหน้าหน่วยหลักสูตร
- เลือกผลการพิจารณา **อนุญาต / ไม่อนุญาต**
- บันทึกเหตุผลประกอบผลการพิจารณา
- บันทึกชื่อผู้พิจารณาและวันเวลาที่ดำเนินการ

หากเลือก **ไม่อนุญาต** ต้องระบุเหตุผลก่อนบันทึกผลการพิจารณา

### 4.4 Workflow Status

กำหนดสถานะคำร้องให้สะท้อนขั้นตอนการพิจารณา เช่น

- Draft — แบบร่าง
- Submitted — ส่งคำร้องแล้ว
- Pending Advisor Review — รอความเห็นอาจารย์ที่ปรึกษา
- Pending Program Head Review — รอความเห็นหัวหน้าหน่วยหลักสูตร
- Pending Final Approval — รอผู้มีอำนาจอนุมัติ
- Approved — อนุญาต
- Rejected — ไม่อนุญาต
- Returned for Revision — ส่งกลับเพื่อแก้ไข
- Cancelled — ยกเลิกคำร้อง

สถานะและลำดับ Workflow ต้องเปลี่ยนตามการดำเนินการจริงของผู้พิจารณา ไม่เปลี่ยนสถานะโดยอัตโนมัติหากยังไม่มีการบันทึกผลในขั้นตอนนั้น

สถานะ Pending ทั้งสามเป็นสถานะเชิงบทบาท ไม่ได้หมายความว่าทุกคำร้องต้องผ่านครบทั้งสามขั้น — คำร้องจะใช้เฉพาะสถานะของขั้นตอนที่มีอยู่จริงตาม `LeaveWorkflowConfig` (ดู §4.7)

### 4.5 Workflow History & Audit Log

ระบบต้องบันทึกประวัติการดำเนินการในแต่ละขั้นตอน ได้แก่

- คำร้องลาอ้างอิง
- ขั้นตอนการพิจารณา
- ผู้ดำเนินการ
- ความเห็นหรือผลการพิจารณา
- เหตุผลประกอบ
- วันและเวลาที่บันทึก
- สถานะก่อนดำเนินการและหลังดำเนินการ

นักศึกษาสามารถติดตามสถานะคำร้องและอ่านความเห็นหรือเหตุผลที่เปิดเผยให้ผู้ยื่นคำร้องทราบได้ โดยต้องควบคุมสิทธิ์การเข้าถึงข้อมูลตาม Role-Based Access Control (RBAC)

### 4.6 Business Rules

1. คำร้องต้องผ่านขั้นตอนตามลำดับ Workflow ที่ผู้ดูแลระบบกำหนด (ค่าเริ่มต้น: อาจารย์ที่ปรึกษา → หัวหน้าหน่วยหลักสูตร → ผู้มีอำนาจอนุมัติ) ก่อนจบการพิจารณา
2. อาจารย์ที่ปรึกษาและหัวหน้าหน่วยหลักสูตรมีหน้าที่บันทึกความเห็น ไม่ใช่ผู้อนุมัติคำร้องหลัก
3. ผู้มีอำนาจอนุมัติเป็นผู้บันทึกผลสุดท้ายว่าอนุญาตหรือไม่อนุญาต พร้อมเหตุผล
4. ห้ามข้ามขั้นตอน Workflow เว้นแต่ผู้ดูแลระบบที่มีสิทธิ์ดำเนินการตามกฎที่กำหนดไว้
5. ความเห็นของอาจารย์ผู้สอนรายวิชาเป็นกระบวนการแยกจาก Approval Workflow หลัก และต้องไม่ทำให้ผลการอนุมัติคำร้องเปลี่ยนแปลงโดยอัตโนมัติ
6. การอนุญาตคำร้องลาหลักและการพิจารณาของอาจารย์รายวิชาต้องแสดงเป็นคนละสถานะ
7. ทุกการเปลี่ยนสถานะต้องบันทึก Audit Log และตรวจสอบสิทธิ์จาก Backend

### 4.7 การตั้งค่าลำดับ Workflow (2–3 ขั้น)

ระบบต้องรองรับ Workflow ที่ยืดหยุ่นได้ โดยผู้ดูแลระบบเป็นผู้กำหนดว่าคำร้องแต่ละกลุ่มต้องผ่านบทบาทใดบ้างและตามลำดับใด

- เก็บการตั้งค่าในโมเดล `LeaveWorkflowConfig` โดยฟิลด์ `steps` เป็นรายการบทบาทเรียงตามลำดับ
- เลือกใช้ชุดขั้นตอนตามขอบเขต ด้วยลำดับความเฉพาะเจาะจงเดียวกับ `LeaveRoleAssignment`:
  กลุ่มเรียน + ภาคการศึกษา > กลุ่มเรียน > หลักสูตร + ภาคการศึกษา > หลักสูตร > ทั้งระบบ
- เงื่อนไขของ `steps` ที่ระบบต้องบังคับใช้ทั้งที่ Serializer และ Service Layer:
  - มีอย่างน้อย 1 ขั้น
  - ค่าต้องเป็นบทบาทที่รู้จัก (`advisor`, `program_head`, `final_approver`)
  - ห้ามใช้บทบาทซ้ำ
  - ต้องเรียงตามลำดับมาตรฐาน advisor → program_head → final_approver
  - ขั้นสุดท้ายต้องเป็น `final_approver` เสมอ
- ตัวอย่างที่อนุญาต: 2 ขั้น `advisor → final_approver`, 2 ขั้น `program_head → final_approver`, 1 ขั้น `final_approver`
- หากไม่มีรายการที่เปิดใช้งานตรงกับคำร้อง ระบบใช้ค่าเริ่มต้น 3 ขั้น (`advisor → program_head → final_approver`)
- รายการตั้งค่าที่ไม่ผ่านเงื่อนไขต้องถูกปฏิเสธที่ Serializer (HTTP 400) และ Resolver ต้อง fallback เป็นค่าเริ่มต้นหากพบข้อมูลเสียในฐานข้อมูล เพื่อไม่ให้การส่งคำร้องของนักศึกษาถูกบล็อก
- สถานะคำร้องยังอิงบทบาทเหมือนเดิม โดยสถานะเริ่มต้นคือสถานะของขั้นแรก และเมื่อแต่ละขั้นบันทึกความเห็น ระบบจะเปลี่ยนไปยังสถานะของขั้นถัดไปจริงตาม `steps`
- หนึ่งขอบเขตเปิดใช้งานได้เพียงชุดเดียว ระบบต้องปฏิเสธการสร้างชุดซ้ำในขอบเขตเดียวกัน (ให้ปิดใช้งานรายการเดิมก่อน)
- การเปลี่ยนหรือลบการตั้งค่ามีผลกับคำร้องที่ส่งใหม่หรือส่งอีกครั้งเท่านั้น คำร้องที่อยู่ระหว่างพิจารณาจะคงขั้นตอนเดิมที่สร้างไว้แล้ว
- การดำเนินการแทนโดยผู้ดูแลระบบ (admin override) ต้องเลือกปลายทางได้เฉพาะบทบาทที่มีอยู่จริงในคำร้องนั้น หาก Workflow ไม่มีขั้นดังกล่าวต้องตอบ HTTP 400

### 4.8 การตั้งค่านโยบายการส่งใบลา (Phase 4)

ผู้ดูแลระบบกำหนดจำนวนวันได้จาก Django admin (`LeavePolicyConfig`) โดยมีได้เพียงแถวเดียวสำหรับทั้งระบบ

| การตั้งค่า | ความหมาย | ค่าเริ่มต้น | ช่วงที่อนุญาต |
|---|---|---|---|
| `personal_advance_days` | ลากิจส่วนตัวต้องส่งล่วงหน้าอย่างน้อยกี่วันก่อนวันเริ่มลา | 3 | 0–30 |
| `sick_normal_grace_days` | ลาป่วยส่งได้ถึงกี่วันหลังวันสิ้นสุดการลาโดยไม่ต้องระบุเหตุผลย้อนหลัง | 1 | 0–7 |
| `sick_late_grace_days` | ลาป่วยผ่อนผันได้ถึงกี่วันหลังวันสิ้นสุดการลา (ต้องระบุ `late_submission_reason`) | 3 | ≥ `sick_normal_grace_days` |
| `medical_certificate_min_days` | ลาป่วยตั้งแต่กี่วันขึ้นไปต้องแนบใบรับรองแพทย์ (นับรวมวันเริ่มและวันสิ้นสุด) | 3 | 1–30 |

- แถวในฐานข้อมูลเป็นแหล่งความจริง admin ไม่ให้เพิ่มแถวที่สองหรือลบแถวเดิม และระบบปฏิเสธค่าที่อยู่นอกช่วงหรือค่าผ่อนผันที่น้อยกว่าค่าส่งปกติ
- ค่าเริ่มต้นมาจาก Django settings เดิม (`LEAVE_PERSONAL_ADVANCE_DAYS`, `LEAVE_SICK_NORMAL_GRACE_DAYS`, `LEAVE_SICK_LATE_GRACE_DAYS`, `LEAVE_MEDICAL_CERTIFICATE_MIN_DAYS`) migration `0006_leavepolicyconfig` สร้างแถวแรกจากค่าเหล่านี้ และใช้ค่า settings เป็น fallback หากแถวถูกลบ
- ทุกการอ่าน (`GET /leave-requests/policy/`, วันกำหนดในคำร้อง, การตรวจเวลาตอนส่ง, และกฎใบรับรองแพทย์) เรียก resolver ตัวเดียวกัน การแก้ค่าใน admin จึงมีผลทันที
- วันกำหนดแสดงผลแบบ live ไม่ได้ snapshot ลงคำร้องเดิม การแก้ไขนโยบายอาจเปลี่ยนวันกำหนดที่คำร้องเก่าแสดงได้
- `resubmit` ยังข้ามการตรวจเรื่องเวลาตามเดิม ส่วนไฟล์แนบและขีดจำกัดอื่น ๆ ยังอ่านจาก settings เหมือนเดิม
- ชื่อฟิลด์ใน API ไม่เปลี่ยน จึงไม่ต้องแก้ Frontend (`LeaveForm` อ่าน `policy.*` เหมือนเดิม)

## 5. Attendance Integration

เมื่อมีการเช็คชื่อในรายวิชาที่นักศึกษาได้ยื่นคำร้องลาไว้ ระบบต้องตรวจสอบความสัมพันธ์ระหว่าง

- นักศึกษา
- คำร้องลา
- ช่วงวันที่และเวลาที่ลา
- รายวิชาและ Section
- วันที่และเวลาของ Attendance Session

หาก Attendance Session อยู่ในช่วงเวลาที่คำร้องลาครอบคลุม ให้แสดงสถานะการลาที่เกี่ยวข้องในหน้าจอเช็คชื่อ

### 5.1 Leave Status in Attendance

สถานะที่อาจแสดง ได้แก่

- Leave Submitted — ยื่นคำร้องลาแล้ว
- Leave Pending Approval — อยู่ระหว่างพิจารณา
- Leave Approved — อนุญาตการลาแล้ว
- Leave Rejected — ไม่อนุญาตการลา
- Leave Not Applicable — ไม่อยู่ในช่วงเวลาการลา

สถานะข้างต้นเป็นตัวอย่างสำหรับออกแบบระบบ ต้องสามารถปรับให้ตรงกับนโยบายจริงของวิทยาลัย

### 5.2 Attendance Business Rules

1. การแสดงสถานะการลาใน Attendance ต้องอ้างอิงข้อมูลคำร้องจริง ไม่ใช้ข้อความที่ผู้ใช้กรอกเอง
2. ห้ามเปลี่ยนสถานะการเข้าเรียนเป็น Present โดยอัตโนมัติจากการยื่นใบลา
3. ห้ามเปลี่ยนสถานะ Attendance เป็น Leave Approved หากคำร้องยังไม่ได้รับอนุมัติ
4. แสดงสถานะการลาแยกจากสถานะการเข้าเรียนอย่างชัดเจน
5. กรณีมีคำร้องหลายรายการครอบคลุม Attendance Session เดียวกัน ต้องจัดการการซ้ำซ้อนอย่างถูกต้อง
6. เมื่อคำร้องถูกอนุมัติ ปฏิเสธ ยกเลิก หรือแก้ไข ให้สถานะที่แสดงใน Attendance สะท้อนข้อมูลล่าสุด
7. การแสดงสถานะต้องคำนึงถึงวัน เวลา Timezone และภาคเรียน
8. การเชื่อมโยงต้องอ้างอิงรหัสนักศึกษาและรหัสรายวิชา/Section ไม่ใช้ชื่อเป็นตัวเชื่อมหลัก

### 5.3 Attendance UI Example

| นักศึกษา | สถานะเข้าเรียน | สถานะคำร้องลา |
|---|---|---|
| นักศึกษา A | ยังไม่เช็คชื่อ | Leave Pending Approval |
| นักศึกษา B | Absent | Leave Approved |
| นักศึกษา C | Present | ไม่มีคำร้องลา |
| นักศึกษา D | Absent | Leave Rejected |

ตารางนี้เป็นเพียงตัวอย่างการแสดงผล ไม่ใช่กฎที่ให้ระบบเปลี่ยนสถานะ Attendance อัตโนมัติ

## 6. Data Model

ออกแบบฐานข้อมูลให้รองรับความสัมพันธ์แบบ One-to-Many ระหว่างคำร้องลาและรายวิชาที่ได้รับผลกระทบ

แนวทาง Entity ที่ควรพิจารณา:

- LeaveRequest
- LeaveWorkflowStep
- LeaveWorkflowHistory
- LeaveCourse
- LeaveCourseReview
- CourseOffering
- CourseSection
- CourseSchedule
- AttendanceSession
- AttendanceRecord

LeaveRequest หนึ่งรายการสามารถมี LeaveCourse ได้หลายรายการ

LeaveCourse แต่ละรายการต้องเชื่อมโยงกับ Course Offering หรือ Section ที่ถูกต้อง และมีข้อมูลการพิจารณารายวิชาแยกกัน

ตรวจสอบ Existing Models และ Database Schema ก่อนเริ่มพัฒนา หลีกเลี่ยงการสร้างตารางหรือฟิลด์ซ้ำกับโครงสร้างเดิม

## 7. User Interface

### 7.1 Student Portal

- สร้างคำร้องลา
- เลือกรายวิชาที่ได้รับผลกระทบแบบ Multi-select
- แสดงวันและเวลาของรายวิชาในช่วงที่ลา
- ตรวจสอบรายการรายวิชาที่เลือก
- แสดงสถานะคำร้องหลัก
- แสดงสถานะการพิจารณารายวิชาแยกรายวิชา
- แสดง Workflow Timeline
- แสดงประวัติและความคิดเห็นของผู้พิจารณา

### 7.2 Instructor Portal

- แสดงคำร้องลาที่เกี่ยวข้องกับรายวิชาที่รับผิดชอบ

- หัวหน้าหน่วยหลักสูตร: บันทึกความเห็น
- ผู้มีอำนาจอนุมัติ: เลือกอนุญาต/ไม่อนุญาต และระบุเหตุผล

- แสดง Workflow Timeline
- ตรวจสอบสิทธิ์ผู้ดำเนินการจาก Backend

### 7.4 Attendance Portal

ในหน้าจอเช็คชื่อ

- แสดงสถานะการลาในแถวของนักศึกษา
- แสดงประเภทการลาและสถานะคำร้อง
- สามารถดูรายละเอียดคำร้องที่เกี่ยวข้องได้
- แยก Leave Status ออกจาก Attendance Status
- ห้ามแก้ไขสถานะการลาโดยอาศัยเพียงการเปลี่ยนสถานะเข้าเรียน

### 7.5 เส้นทางหน้าจอที่ใช้งานจริง (Phase 1–4)

| เส้นทาง | ผู้ใช้ | หน้าที่ |
|---|---|---|
| `/student/leaves` | student | รายการใบลา ตัวกรองสถานะ และ pagination |
| `/student/leaves/new` | student | สร้างใบลา เลือกรายวิชา และแนบเอกสาร |
| `/student/leaves/[id]` | student | รายละเอียด Workflow Timeline และปุ่มส่ง/ส่งอีกครั้ง/ยกเลิก |
| `/instructor/leaves` | instructor | คำร้องในรายวิชาที่รับผิดชอบ |
| `/instructor/leaves/[id]` | instructor | บันทึกความเห็นรายวิชา (แยกจาก Workflow หลัก) |
| `/approvals` | instructor, admin | คิวพิจารณาตามขั้นตอน (instructor เห็นเฉพาะขั้นของตน) |
| `/approvals/[id]` | instructor, admin | บันทึกความเห็น ส่งกลับ และดำเนินการแทน (admin) |
| `/admin/leave-roles` | admin | มอบหมาย `LeaveRoleAssignment` |
| `/admin/leave-workflow` | admin | ตั้งค่าลำดับขั้นตอน `LeaveWorkflowConfig` (2–3 ขั้น) พร้อมตัวอย่างลำดับ |
| `/leaves/[id]/print` | student, instructor, admin | พิมพ์ A4 ตามขอบเขตสิทธิ์ (instructor เห็นเฉพาะรายวิชาตน) |

`LeaveRoleAssignment` เป็นแหล่งความจริงเดียวของผู้รับผิดชอบ Workflow ลำดับความเฉพาะเจาะจงคือ
กลุ่มเรียน + ภาคการศึกษา > กลุ่มเรียน > หลักสูตร + ภาคการศึกษา > หลักสูตร > ทั้งระบบ
อาจารย์ที่ปรึกษาและหัวหน้าหน่วยหลักสูตรต้องมีขอบเขตอย่างน้อยหนึ่งระดับ ส่วนผู้อนุมัติกำหนดระดับทั้งระบบได้
หาก resolve ผู้รับผิดชอบไม่ครบตอนส่งคำร้อง ระบบต้องปฏิเสธการส่ง (HTTP 400) และนักศึกษาต้องติดต่อผู้ดูแลระบบ

## 8. Authorization & Security

ใช้ Role-Based Access Control (RBAC) ตามระบบเดิม

- นักศึกษาเข้าถึงคำร้องของตนเอง
- อาจารย์เข้าถึงคำร้องที่เกี่ยวข้องกับรายวิชาที่รับผิดชอบ
- อาจารย์ที่ปรึกษาเข้าถึงคำร้องของนักศึกษาที่ตนรับผิดชอบ
- หัวหน้าหน่วยหลักสูตรเข้าถึงคำร้องตามหลักสูตรที่ได้รับมอบหมาย
- ผู้มีอำนาจอนุมัติเข้าถึงคำร้องในขั้นตอนอนุมัติ
- ผู้ดูแลระบบสามารถจัดการตามสิทธิ์ที่ได้รับ

ตรวจสอบสิทธิ์ฝั่ง Backend ทุกครั้ง ห้ามพึ่งพาการซ่อนปุ่มใน Frontend เพียงอย่างเดียว

บันทึก Audit Log สำหรับการส่งคำร้อง การแก้ไข การพิจารณา และการเปลี่ยนสถานะ ป้องกันการแก้ไขข้อมูลคำร้องหรือผลพิจารณาโดยผู้ไม่มีสิทธิ์

### 9.1 Endpoint ที่ใช้งานจริง

| Endpoint | สิทธิ์ | หน้าที่ |
|---|---|---|
| `GET/POST /leave-requests/` | student (ของตน), admin | รายการ/สร้างคำร้อง |
| `POST /leave-requests/{id}/submit/` | student เจ้าของ | ส่งคำร้องและ resolve ผู้รับผิดชอบตามขั้นตอนที่ตั้งค่าไว้ |
| `POST /leave-requests/{id}/resubmit/` | student เจ้าของ | ส่งใหม่หลังถูกส่งกลับ เริ่มที่ขั้นแรกของ Workflow ปัจจุบัน |
| `POST /leave-requests/{id}/cancel/` | student เจ้าของ | ยกเลิกระหว่างพิจารณา |
| `GET /leave-requests/{id}/history/` | ผู้มีสิทธิ์เห็นคำร้อง | Workflow History |
| `POST /leave-requests/{id}/admin-override/` | admin | ดำเนินการแทน (ต้องมีเหตุผล) |
| `GET /leave-approvals/` | instructor, admin | คิวพิจารณา (instructor เฉพาะขั้นของตน) |
| `POST /leave-approvals/{id}/advisor-opinion/` | advisor ปัจจุบัน | บันทึกความเห็นและส่งต่อ |
| `POST /leave-approvals/{id}/program-head-opinion/` | program head ปัจจุบัน | บันทึกความเห็นและส่งต่อ |
| `POST /leave-approvals/{id}/final-decision/` | final approver ปัจจุบัน | อนุมัติ/ไม่อนุมัติ |
| `POST /leave-approvals/{id}/return/` | advisor/program head ปัจจุบัน | ส่งกลับเพื่อแก้ไข |
| `GET/POST/PATCH/DELETE /leave-role-assignments/` | admin | จัดการ `LeaveRoleAssignment` |
| `GET/POST/PATCH/DELETE /leave-workflow-configs/` | admin | จัดการ `LeaveWorkflowConfig` (ลำดับขั้นตอน 2–3 ขั้นตามขอบเขต) |
| `GET /leave-requests/{id}/print/` | student, instructor, admin | เอกสารพิมพ์ A4 ตามขอบเขตสิทธิ์ |
| `GET /leave-requests/policy/` | student, instructor, admin | นโยบายการส่งใบลาที่ resolve จาก `LeavePolicyConfig` (หรือ settings เมื่อไม่มีแถว) |

`available_actions` ใน payload ของคำร้องใช้บอก Frontend ว่าผู้ใช้ปัจจุบันทำอะไรได้
แต่ทุก endpoint ต้องตรวจสอบขั้นตอนปัจจุบัน ผู้รับผิดชอบ และสิทธิ์ซ้ำที่ Service Layer เสมอ

ตรวจสอบข้อมูลและสิทธิ์ใน Django Backend

การคำนวณสถานะที่เชื่อมโยงกับ Attendance ต้องดำเนินการที่ Backend หรือ Service Layer ที่เชื่อถือได้ ไม่ให้ Frontend เป็นผู้กำหนดผลลัพธ์เอง

### 11.1 ข้อกำหนดก่อน Deploy (Workflow ยืดหยุ่น)

- ต้องรัน migration ของแอป `leaves` ก่อนเปิดใช้งานฟีเจอร์ (migration `0005_leaveworkflowconfig` และ `0006_leavepolicyconfig`)
  ผ่านขั้นตอน deploy ของผู้ดูแลระบบ (Coolify UI) — ห้ามรัน migration ด้วยมือบน Production โดยไม่มีการสำรองข้อมูล
- migration `0006_leavepolicyconfig` สร้างแถวตั้งค่านโยบายจากค่า settings ปัจจุบัน ตรวจสอบค่าใน Django admin หลัง deploy ก่อนเปิดให้นักศึกษาส่งคำร้อง
- ฐานข้อมูล Production คือ Supabase PostgreSQL การรัน migration ต้องสำเร็จก่อน deploy Frontend เวอร์ชันที่เรียก `/leave-workflow-configs/`
- หลัง migrate ระบบใช้งานได้ทันทีโดยไม่ต้องสร้างข้อมูลตั้งค่า เนื่องจากไม่มีรายการที่เปิดใช้งาน = ใช้ Workflow เริ่มต้น 3 ขั้น
- ต้องมี `LeaveRoleAssignment` ครบทุกบทบาทที่ใช้จริงในแต่ละขอบเขต มิฉะนั้นการส่งคำร้องจะถูกปฏิเสธ (HTTP 400) พร้อมระบุบทบาทที่ขาด
- ไฟล์แนบเก็บแบบ private ที่ `backend/private_media` และดาวน์โหลดผ่าน endpoint ที่ตรวจสิทธิ์ — ต้องคงตำแหน่งและสิทธิ์นี้ใน Production

## 12. Development Instructions

ก่อนพัฒนา:

1. สำรวจโครงสร้าง SAMS ปัจจุบัน
2. ตรวจสอบ Models, APIs, Authentication, Authorization และ Attendance Workflow เดิม
3. ตรวจสอบความสัมพันธ์ของนักศึกษา รายวิชา Section ตารางเรียน และ Attendance
4. วางแผนการเชื่อมโยง Leave Workflow กับระบบเดิม
5. รักษาโครงสร้างและรูปแบบ UI เดิม
6. ห้ามสร้าง Mock Data สำหรับใช้งานจริง
7. ห้ามทำให้ระบบเช็คชื่อเดิมเสียหาย
8. พัฒนาให้รองรับข้อมูลจริงและการขยายระบบในอนาคต
9. ตรวจสอบความถูกต้องของ Approval Workflow และ Course-specific Review ก่อนนำไปใช้งาน
10. หากพบข้อกำหนดที่ไม่ชัดเจน ให้แยกเป็น Configuration หรือรายงานข้อกำหนดที่ต้องยืนยัน ห้ามกำหนดนโยบายใหม่แทนวิทยาลัยโดยพลการ

ให้ดำเนินการพัฒนา Feature นี้แบบ End-to-End ทั้ง Frontend, Django Backend, Database, Authorization, Workflow และ Attendance Integration
